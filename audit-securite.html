Audit sécurité · Septembre 2026

La confidentialité est le produit.
Le socle est déjà sérieux.

Sub Rosa promet que les prompts, l'audio et les notes ne quittent pas le contrôle de l'utilisateur — et le code tient cette promesse : secrets en keychain jamais exposés au webview, SQL entièrement paramétré, CSP stricte sans eval ni innerHTML de données modèle, CORS en deny-all, backend qui échoue fermé. L'audit relève zéro vulnérabilité critique et trois axes de durcissement réels : le http:// accepté pour la clé, l'héritage du token sidecar par les processus enfants, et l'absence de scan CVE continu.

01 · Stockage des secrets (keychain)

9 / 10

Desktop + iOS · Le coffre-fort est bien construit

Constat

  • Sain. La clé cdm_ vit dans le keychain OS via keyring, service dédié xyz.carpediem.subrosa.carpe-diem (suffixe -dev en debug) — settings.rs:29-32.
  • Elle n'est jamais renvoyée au webview : le DTO n'expose que has_api_key (settings.rs:54-72). Le token issue-report et la clé Google Places suivent le même régime.
  • Faible validate_base_url accepte http:// (settings.rs:893) — un utilisateur distrait peut faire transiter son bearer en clair.
  • Info Le bypass debug SUBROSA_DEV_API_KEY est #[cfg(debug_assertions)] — absent du binaire release. Propre.

Plan vers 10/10

  1. Refuser http:// hors loopback

    Dans validate_base_url : https:// obligatoire, sauf http://127.0.0.1/localhost (utile en dev). Un avertissement explicite au collage d'un base non chiffré, pas une erreur silencieuse.

  2. Test d'inventaire keychain

    Un test Rust qui liste les services créés par l'app et échoue si un secret atterrit ailleurs que dans un service keychain dédié — garantit que le futur code n'introduit pas de fichier plat de secrets.

  3. Rotation guidée

    Dans les réglages Connexion : un bouton « Remplacer la clé » qui écrit la nouvelle puis vérifie via /v1/credits avant de supprimer l'ancienne — une rotation sans fenêtre d'échec.

Effet 10/10 : impossible, même en se forçant, de stocker ou transmettre la clé hors d'un canal chiffré — et la rotation devient un geste de routine.

02 · Le sidecar (token, port, variables d'environnement)

8 / 10

Desktop + mobile · Le cœur de l'architecture

Constat

  • Sain. Bind forcé sur 127.0.0.1 (sidecar.rs:489, mobile dur-codé dans embed/src/lib.rs:58), port éphémère, bearer éphémère UUIDv4 vérifié sur chaque route (LocalDevTokenVerifier), CORS deny-all (CorsLayer::new()).
  • Moyen Le token et la clé vivent dans l'environnement des processus : OS_JUNE_LOCAL_DEV_BEARER_TOKEN est hérité par tous les enfants (Hermes, helpers de dictation) via sidecar.rs:339-342, 495-496. Hermes est sandboxé (sandbox-exec), mais tout compromis d'un enfant donne accès au sidecar « as user ».
  • Info Le port est exposé via l'event de statut au webview — nécessaire, mais accroît l'importance du token.
  • Info Le token est un UUIDv4 (122 bits CSPRNG) : correct ; 256 bits hex serait plus défensif.

Plan vers 10/10

  1. Laver l'environnement des enfants non autorisés

    Les spawns de Hermes/helpers passent une env explicitement construite (allowlist) qui retire OS_JUNE_LOCAL_DEV* et JUNE__UPSTREAMS__*, sauf pour le sidecar lui-même. 20 lignes dans le wrapper de spawn — réduit le blast radius d'un enfant compromis à zéro.

  2. Passer le token par stdin, pas par env

    Le sidecar lit son token en première ligne de stdin au démarrage (option déjà naturelle dans june-embed). L'env ne contient plus aucun secret ; les secrets n'apparaissent plus dans ps eww.

  3. Token 256 bits

    Remplacer Uuid::new_v4() par rand::random::<[u8;32]>() encodé hex. Trivial, aligné sur la convention des tokens locaux.

  4. Pin par génération documenté

    Le compteur de génération qui invalide les health checks obsolètes existe déjà — ajouter un test qui prouve qu'un token d'une génération précédente est refusé après redémarrage du sidecar.

Effet 10/10 : aucun secret ne transite par l'environnement de processus, et la compromission d'un helper ne donne plus aucun accès au moteur d'inférence.

03 · CSP & durcissement du webview

8 / 10

Desktop · La muraille du webview

Constat

  • Sain. script-src 'self' + un hash sha256 épinglé, object-src 'none', base-uri 'none', frame-ancestors 'none' (tauri.conf.json:80). Aucun eval, aucun chargement de script distant dans src/.
  • Faible connect-src http://127.0.0.1:* ws://127.0.0.1:* : conséquence assumée du port aléatoire du sidecar, mais un XSS dans le webview pourrait sonder les autres services locaux de la machine.
  • Info style-src 'unsafe-inline' — usage Tauri standard, risque résiduel faible mais inutile à long terme.

Plan vers 10/10

  1. Resserrer connect-src

    Épingler le schéma authentifié : au lieu de tout loopback, n'autoriser que ipc: + le schéma d'asset + un connect du côté Rust (le webview parle au sidecar via les commandes Rust pour tout sauf le streaming, déjà vrai en grande partie). Chaque retrait de portée est une victoire permanente.

  2. Sortir les styles inline du chemin principal

    Transférer progressivement les styles inline dans les feuilles, puis tenter style-src 'self' avec un rapport d'exception. Faible priorité, mais le 10/10 se joue sur ces derniers pourcents.

  3. Un test CSP en CI

    Un test qui parse tauri.conf.json et échoue si la CSP s'élargit (nouveau unsafe-eval, *, retrait de frame-ancestors). La CSP devient une propriété gardée, pas une config oubliée.

Effet 10/10 : même un XSS hypothétique dans le webview ne peut ni exécuter du code, ni joindre un autre service local, ni charger une ressource distante.

04 · Rendu markdown & injection (XSS)

9 / 10

Desktop + mobile · La sortie du modèle n'écrit pas d'HTML

Constat

  • Sain. Zéro dangerouslySetInnerHTML dans src/ ; les deux moteurs markdown (simple-markdown.tsx, le renderer desktop AgentWorkspace.tsx:12569-12635) émettent des nœuds React échappés par construction. Pas de marked/react-markdown avec pass HTML.
  • La note round-tripe par le document ProseMirror, jamais par le DOM (ADR-0037) ; isAllowedUri bloque javascript: dans les notes (extensions.ts:46-47).
  • Les blocs subrosa:* exigent safeHttpsUrl() et dégradent en bloc de code sinon (chat-blocks.ts:131-141).
  • Faible simple-markdown.tsx:341,357 : le matcher mobile accepte n'importe quel href entre parenthèses — un [text](javascript:alert(1)) sorti d'un modèle rend une ancre cliquable sans garde https (le desktop, lui, ne matche que https?://).

Plan vers 10/10

  1. Uniformiser la garde https sur mobile

    Appliquer le même filtre que le desktop dans renderInline() : seul un href https:// devient une ancre ; tout le reste reste du texte. Aligner les deux moteurs — et ajouter un test de corpus commun mobile = desktop.

  2. Valider window.open des artefacts url

    AgentWorkspace.tsx:6764 passe artifact.path (URL rapportée par un outil) directement à window.open. Passer par openExternalUrl comme partout — un seul point de contrôle pour toute navigation.

  3. Corpus anti-XSS exécuté en test

    Un vitest qui passe une liste de charges (javascript:, data:, onerror=, liens imbriqués, caractères unicode homoglyphes) aux deux renderers et asserte qu'aucune ancre non-https et aucun attribut d'événement n'en sort. Le correctif devient une propriété permanente.

Effet 10/10 : aucune sortie de modèle — chat, note, artefact — ne peut déclencher une navigation ou un script, prouvé par un corpus de tests partagé.

05 · Ouverture de liens & deep links

8,5 / 10

Desktop + mobile · La frontière du navigateur

Constat

  • Sain. Double contrôle : le frontend ne passe que du https (openExternalUrl) et le Rust re-valide schéma + rejet des caractères de contrôle (open_url.rs:14-30). rel="noreferrer" partout.
  • Sain. Les deep links subrosa:// sont traités comme hostiles par conception (destinations.ts:18-21) : un seul segment, ids ^[\w-]{1,64}$, query ≤ 200 chars, .. rejeté avant normalisation, re-vérification Rust, suite de tests dédiée.
  • Faible McpServersSection.tsx:664-673 rend login.authUrl (contrôlé par le serveur MCP) comme href sans validation de schéma côté webview.
  • Faible onRecoverRecording et les commandes fichier Hermes restent à tracer complètement (voir fiche 10).

Plan vers 10/10

  1. Valider authUrl comme tout lien

    Passer login.authUrl par le même garde https + re-validation Rust. Un point d'entrée de moins qui croit « connaître son serveur » : tout ce qui traverse IPC est hostile, y compris ce qui vient d'un serveur qu'on a choisi.

  2. Allowlist de schémas centralisée

    Une constante unique ALLOWED_OPEN_SCHEMES = ["https:"] consommée par open_external_url, les renderers, les artefacts et MCP — un seul endroit à faire évoluer, un seul à tester.

  3. Fuzz des destinations

    Générer 10 000 deep links aléatoires dans un test (subrosa://import?url=… inclus) et asserter que parseDestination ne produit jamais de commande hors de son enum. Le parseur est déjà strict ; le fuzz le prouve en continu.

Effet 10/10 : une seule porte de sortie vers le navigateur, une seule porte d'entrée via deep link, toutes deux allowlistées et fuzzées.

06 · SSRF & fetch réseau

9 / 10

Desktop + sidecar · Le produit ne scrute pas, il ne rapporte pas

Constat

  • Sain. Aucun forwarding d'URL arbitraire : l'upstream est fixé au spawn ; les model ids sont whitelistés contre la table de prix (require_priced_model dans tous les handlers) — le client ne peut pas faire du sidecar un relais arbitraire.
  • Sain. Le fetch web a de vraies défenses : HTTPS-only, préflight DNS exigeant des IP toutes publiques, checks NAT64/IPv6 locaux, tests étendus (web.rs:204-329).
  • Sain. june_api_url() échoue fermé, sans fallback distant (june_api.rs:1300-1316) — les prompts ne peuvent pas atterrir silencieusement ailleurs (ADR-0017).
  • Info Les routes de santé (/livez, /verify) sont non authentifiées par design — contenu statique HTML-échappé, testé pour ne rien révéler de plus.

Plan vers 10/10

  1. Préflight DNS pour le proxy média Studio

    Le proxy Carpe Diem (media.rs) est allowlisté par chemin — ajouter le même préflight DNS public-IP que web.rs pour l'hôte résolu, pour que les deux chemins réseau partagent la même règle.

  2. Un test « l'app ne parle qu'à sa liste »

    Un test d'intégration qui intercepte le réseau (ou lit la constante des bases autorisées) et échoue si un nouveau domaine entre en egress sans passer par validate_base_url ou la allowlist. L'inventaire des destinations devient une propriété testée.

  3. Timeouts et tailles bornées partout

    Vérifier que chaque client reqwest porte un timeout + une limite de taille de réponse (le fetch web le fait ; auditer memory/recall et media). Un service local qui n'expire jamais est un DoS de soi-même.

Effet 10/10 : aucun chemin réseau ne peut être retourné contre la machine de l'utilisateur, et l'app reste incapable de contacter autre chose que ce que l'utilisateur a configuré.

07 · SQL & intégrité des données locales

9,5 / 10

Desktop + mobile · La base locale

Constat

  • Sain. sqlx partout, tout passe par .bind() ; les seuls format! dans le SQL interpolent des constantes de compilation (MEMORY_COLUMNS, placeholders ?). Les LIKE échappent \ % _ avec ESCAPE '\' (repositories.rs:587-593).
  • Migrations versionnées 001-019, découpe sur ; documentée, Cargo.lock commis — reproductible.
  • Info La base n'est pas chiffrée au repos (SQLCipher absent). Cohérent avec la menace visée (le réseau, pas le vol de disque — le keychain protège la clé), mais un gap face à la menace « laptop saisi ».

Plan vers 10/10

  1. Une règle lint anti-SQL-dynamique

    Un test qui scanne src-tauri/src/db/ pour tout format! contenant SELECT/INSERT/UPDATE/DELETE avec une variable non constante — échoue à la compilation CI. Le pattern actuel est bon ; le rendre intouchable.

  2. SQLCipher en option documentée

    Migrer la base vers SQLCipher (clé dérivée via le keychain, clé de chiffrement locale distincte de la clé API) OU documenter explicitement l'ADR de non-chiffrement avec la menace écartée. Les deux valent 10/10 ; l'oubli de la question, non.

  3. Export chiffré

    L'export de notes en clair est une feature ; offrir un export chiffré (mot de passe, AES-GCM via age ou équivalent) pour l'archivage. La confidentialité jusqu'au bout du cycle de vie.

Effet 10/10 : l'injection est structurellement impossible et prouvée en CI, et le repos n'est plus une exception non-discutée.

08 · Updateur & signature

9 / 10

Desktop · Le canal de mise à jour

Constat

  • Sain. Clé publique minisign épinglée dans tauri.conf.json:113 ; endpoint GitHub public dédié (sub-rosa-releases) ; le frontend ne fetch jamais d'URL de mise à jour — tout vit en Rust (updater.ts n'appelle que des commandes).
  • La comparaison de versions centralise la logique anti-downgrade avec tests (updates.rs:440-511). macOS signé + notarisé, Windows NSIS signé — secrets uniquement en secrets.* GitHub.
  • Info L'override runtime de l'endpoint est restreint aux deux constantes (stable/rc) — pas d'URL arbitraire.

Plan vers 10/10

  1. Tester le rejet d'update non signé

    Un test bout-en-bout (fixture latest.json signée par une mauvaise clé) qui asserte le refus. La signature est le pivot de tout le modèle de confiance — elle mérite son test négatif.

  2. Rétention des signatures

    Conserver les manifests latest.json historiques signés dans le repo de releases : un utilisateur en v1.2 doit toujours pouvoir remonter un chemin de mises à jour signées, même si l'endpoint actuel a changé.

  3. Transparence de provenance

    Afficher dans l'écran de mise à jour la version cible, sa date et le canal — l'utilisateur confirme vers quoi il met à jour. La sécurité se vit aussi dans la clarté.

Effet 10/10 : le canal de mise à jour, déjà signé, devient testé négativement et lisible par l'utilisateur.

09 · Supply chain & CI sécurité

7 / 10

Dépôt + GitHub Actions · Le maillon manquant est la surveillance

Constat

  • Sain. repository-hygiene.yml : actions externes épinglées sur SHA 40 caractères, scan de .env/clés privées, garde-fous de fork (ADR-0017). Cargo.lock commis. Aucun secret dans le dépôt (grep cdm_/sk-/ghp_ : une seule string de test, qui vérifie la rédaction).
  • Sain. TLS via rustls partout, pas d'openssl-sys (Cargo.toml:39 des deux workspaces).
  • Moyen Aucun scan de vulnérabilités : ni cargo audit, ni cargo-deny, ni Dependabot dans les workflows ou le Makefile. Les CVE connues des dépendances ne sont jamais vérifiées.
  • Faible Le runtime Hermes est téléchargé au lancement depuis une URL GitHub épinglée (hermes_bridge.rs:44,53) — l'intégrité repose sur l'URL épinglée ; la vérification de hash post-téléchargement est à confirmer.

Plan vers 10/10

  1. Un job cargo-audit hebdomadaire

    Workflow mensuel + sur pull_request (path-filter Cargo) : cargo audit sur les deux lockfiles, échec sur CVE moyenne+. Le gap n°1 de l'audit, et il coûte 30 lignes de YAML.

  2. cargo-deny pour les licences et les sources

    Interdire les crates à sources floues,.dupliquer les advisories, geler les déps wildcard. L'app porte un runtime d'agent : sa chaîne de dépendances mérite le même traitement que son code.

  3. Hachage vérifié du runtime Hermes

    Épingler le hash de l'archive (pas seulement l'URL) dans le code, vérifier après téléchargement, échouer fermé sinon. Le pin par hash transforme un téléchargement en intégrité vérifiable.

  4. Dependabot minimal

    dependabot.yml pour les deux workspaces Cargo + npm, hebdomadaire. Complète l'audit passif par la remontée proactive.

Effet 10/10 : la supply chain est scanée en continu — une CVE publiée un mardi est détectée le mercredi, pas à la prochaine release.

10 · Surface IPC & confinement des chemins

8 / 10

Desktop + mobile · ~250 commandes, une seule à compléter

Constat

  • Sain. Capabilities Tauri minimales : les fenêtres HUD ne peuvent invoquer que des events (hud.json), pas de plugin fs/shell/http, SQLite hors webview.
  • Sain. Les commandes média verrouillent les chemins : is_within_gallery, rejet de ParentDir, allowlist d'extensions, tests dédiés (media.rs:859-880). L'export timeline écrit sous les répertoires app. L'ingest de liens a des tests SSRF/traversal.
  • Faible download_hermes_bridge_file / save_hermes_bridge_file / copy_hermes_bridge_file_to_clipboard (lib.rs:284-291) : opèrent sur le snapshot du répertoire Hermes — le confinement de chemin n'est pas prouvé par test, et le fichier fait ~11k lignes.
  • Info Aucune commande n'exécute un shell construit depuis l'IPC ; les appels process sont des binaires fixes avec args structurés.

Plan vers 10/10

  1. Prouver le confinement Hermes par test

    Reprendre le pattern des tests médias : une commande de bridge qui tente ../../ hors du working dir doit échouer, et ce test vit à côté des autres (tests/). Trois commandes, trois tests.

  2. Un helper confined_path() unique

    Factoriser la vérification (racine + canonicalisation + rejet de ..) dans une fonction unique utilisée par média, timeline, bridge et export. Un seul endroit à auditer pour toujours.

  3. Inventaire IPC testé

    Le test shared_commands.rs existe pour la parité desktop/mobile — l'étendre : toute nouvelle commande qui prend un chemin doit référencer le confinement utilisé, sinon échec de build. La surface IPC est gardée par la compilation.

Effet 10/10 : chaque commande qui touche le disque passe par le même confinement testé, et l'ajout d'une commande non confinée échoue en CI.

11 · Journalisation & fuite de secrets

9 / 10

Transversal · Ce que l'app écrit sur disque

Constat

  • Sain. Les providers june-api ne loggent que %url %status %error et les longueurs de corps — jamais de headers ni de clés (venice.rs:105-147). Les erreurs remontent des codes génériques, pas les corps upstream.
  • Sain. Le stdout/stderr du sidecar va dans june-api.log du répertoire logs — vérifié sans clé.
  • Faible Aucun garde-fou automatique : un futur tracing::debug!("{req:?}") imprimerait des headers sans que rien ne l'attrape.

Plan vers 10/10

  1. Un test anti-fuite sur les logs

    Un test d'intégration qui exerce les chemins d'erreur des providers avec une clé factice et asserte qu'elle n'apparaît nulle part dans les logs produits. La propriété « la clé n'est jamais loggée » devient exécutable.

  2. Redaction structurelle

    Un type Redacted<String> (Debug/Display masqués) pour tout secret qui circule dans la config runtime — l'oubli de masquage devient une erreur de compilation, pas une révision manuelle.

  3. Rotation du log sidecar

    Borner june-api.log (taille + nombre de fichiers) : un log qui grossit indéfiniment est à la fois un problème de disque et une surface de rétention.

Effet 10/10 : impossible de fuiter un secret par log par accident — le compilateur et les tests en garantissent la propriété.

12 · iOS & mobile

9 / 10

iPhone · Le keychain jusqu'au bout

Constat

  • Sain. La clé cdm_ vit dans le Keychain iOS via keyring ; le sidecar embarqué reçoit la clé en mémoire via EmbedOptions — pas d'env, pas d'UserDefaults (sidecar.rs:382-388).
  • Sain. Le localStorage ne contient que de l'état UI (galerie = index de chemins, jamais de bytes, jamais de secrets). Info.plist : permissions décrites et scopées, BGTask ids alignés avec ios_background.rs.
  • Faible Les artefacts média transissent en base64 data: dans le webview iOS — correct, mais de gros data: URLs consomment de la mémoire webview et affaiblissent les marges de rendu ; la limite de taille par artefact mérite d'être explicite.

Plan vers 10/10

  1. Plafond de taille des data URLs

    Refuser ou paginer au-delà d'un seuil (ex. 25 Mo) avec un message clair — protège à la fois la mémoire du webview et la lisibilité de la surface d'attaque.

  2. Keychain access control documenté

    Vérifier et documenter les attributs keychain iOS (kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly) : le secret ne quitte pas l'appareil, même via une sauvegarde iCloud non chiffrée.

  3. Exclusion de sauvegarde pour les médias

    Marquer le répertoire galerie isExcludedFromBackup — les rendus générés ne méritent pas de gonfler un backup iCloud, et la règle réduit la copie hors appareil.

Effet 10/10 : le téléphone ne détient rien que le keychain ne protège, et rien de lisible ne quitte l'appareil par une voie passive (backup, log, data URL démesurée).

13 · Menace produit : la promesse de confidentialité

8 / 10

Transversal · Le modèle de menace visible par l'utilisateur

Constat

  • Sain. L'architecture défend la promesse : pas d'OS Accounts, pas de hosted API, june_api_url() sans fallback distant, /verify décrit le loopback, ADR-0017 verrouille l'autonomie produit.
  • Moyen La promesse n'est ni testée ni mesurable : rien en CI n'échoue si un chemin réseau sort de l'inventaire des destinations autorisées, rien ne prouve qu'un prompt ne peut pas atteindre un endpoint non déclaré.
  • Info La télémétrie de cache passe par des headers bornés (ADR-0023) — documenté, mais l'utilisateur n'a nulle part où voir ce qui part.

Plan vers 10/10

  1. Un test « egress zero-surprise »

    Un test d'intégration qui détourne le DNS/reqwest vers un collecteur et exerce tous les flux (chat, dictation, memory, studio, updater) — tout host non inscrit dans la liste déclarée fait échouer le test. La promesse « rien ne part ailleurs » devient une assertion, pas un argument.

  2. Une page « Ce qui part, ce qui reste »

    Dans les réglages, un écran lisible : le base Carpe Diem (vos demandes), l'updater (vérification signée), le reste — tout — local. Cohérent avec /verify ; transforme l'architecture en preuve visible.

  3. Modèle de menace écrit

    Un docs/threat-model.md d'une page : actifs (clé, prompts, audio, notes), frontières (keychain, loopback+token, webview sandboxé, upstream), menaces hors périmètre (root local, disque chiffré OS). C'est le document qui rend l'audit reproductible par un tiers.

Effet 10/10 : la confidentialité n'est plus une affirmation marketing mais une propriété testée en CI et démontrable à l'utilisateur en une page.
