# ADR 0055: A native sign-in comes back through a deep link

- Status: accepted
- Date: 2026-09-20

## Context

Signing an app in to a Sub Rosa account takes six moves. The app shows an eight
character code, opens a browser, the person authenticates, finds the code they
were shown, types it, presses "Authorize this app", and comes back. Then the
app polls until the service agrees. Three more guided steps follow before any
note moves.

The device flow was chosen deliberately.
[ADR-0049](0049-accounts-synchronise-ciphertext-without-hosting-inference.md)
says why: "The device flow uses a browser approval plus PKCE-bound one-use
exchange. It avoids depending on a registered universal-link domain before one
exists."

That reason has expired. The `subrosa` scheme is registered on all four
platforms — `tauri.conf.json` for desktop, `CFBundleURLTypes` on iOS, an
`intent-filter` on Android — `tauri-plugin-deep-link` is already a dependency,
and the account service has been in production on its own domain since
2026-09-18. Nothing is waiting on a domain any more.

What the code bought was not only convenience. It was a human approval: the
code travels from the app to the person, and approving it is an explicit POST
from a browser authenticated in the last five minutes. Remove the code and the
naive replacement reopens exactly what it guarded. An attacker starts a request
with their own PKCE verifier, sends the victim the real start link on the real
domain with the real certificate, the victim signs in, and the attacker
exchanges their verifier for a session on the victim's account.

## Decision

**The app opens the real sign-in page and the browser hands the session back
through `subrosa://auth/callback`. What replaces the human approval is a
binding in two halves, carried on two channels, and the exchange demands
both.**

- **Half one, the PKCE verifier.** Generated by the app, written to the OS
  keyring before the browser opens, never sent anywhere until the exchange. It
  proves *which instance of the app started this*.
- **Half two, the return code.** Two hundred and fifty six bits, generated by
  the service at the callback — that is, only once somebody has actually
  authenticated — and delivered only in the deep link. It proves *which machine
  finished this*.

Neither half is enough. In the attack above, the attacker holds the verifier
and the return code goes to the victim's own machine. An application squatting
the `subrosa` scheme holds a return code and not the verifier. Both are
refused, fail-closed, in one match in `exchange_device`.

Supporting decisions, each load-bearing:

- **The service stays the only OIDC client.** Keycloak's registered redirect
  remains `{account_origin}/auth/callback` and never learns a custom scheme.
  Redirects to custom schemes at an identity provider are an entire family of
  vulnerabilities, avoided here by construction.
- **Which flow is finishing is decided by the row the single-use `state`
  consumes**, through a `native_request_id` column on `login_attempts`. Nothing
  the caller supplies chooses the branch.
- **A native callback sets no session cookie.** Approving a device used to
  leave a twelve hour browser session with step-up powers in whatever browser
  happened to be open. The native flow has no use for one.
- **The return code rides in the URL fragment**, so it reaches neither the
  service nor a `Referer`, the same discipline the pairing QR already uses. An
  interstitial page at `/account/devices/return` reads it, removes it from the
  address bar with `history.replaceState`, and opens the deep link. A `303`
  straight to a custom scheme is blocked or erratic depending on the browser,
  so the page is not optional.
- **The service never receives a destination.** The return page is a constant
  in the service and the scheme is a constant in the page. A validated
  redirect parameter is still a redirect parameter, and somebody eventually
  reads it as configuration.
- **`/api/v1/device-login*` and the eight character code stay**, as a declared
  fallback behind "The page did not come back?", reachable from the sign-in
  card. Apps already shipped keep using it untouched: they send no `native`
  flag, so they get exactly the response they got before.

## Residual risks, stated rather than hidden

- **Scheme squatting.** On macOS, Windows and Android another application can
  register `subrosa` and receive the return code. Without the verifier it gets
  nothing. The real fix is a universal link or app link claiming
  `/account/devices/return`, which is deliberately not in this change.
- **An unsolicited sign-in.** A link from somebody else still makes the victim
  authenticate on their own account. Nothing is granted, and the app says so in
  as many words rather than failing quietly: `account_login_unsolicited`.
- **The return code passes through the webview** on its way from the deep link
  handler. It is worthless without the verifier, which is read only by Rust,
  and `parseDestination` drops the query rather than carrying it inward.

## Consequences

- Signing in is one press, a password or passkey on the real page, and the app
  comes back by itself.
- `max_age=0` is unchanged, so the password is asked for every time. That is
  intended, and the copy says so.
- Development on macOS cannot exercise the deep link from `pnpm tauri:dev`:
  debug and release share the bundle identifier `xyz.carpediem.subrosa`, so the
  operating system cannot tell the two apart and a second `subrosa-dev` scheme
  would not disambiguate them either. Test the native return on a built bundle,
  or use the code fallback in development.

## Alternatives rejected

- **A loopback listener (RFC 8252) on desktop.** A socket the app opens during
  sign-in, for a case the existing fallback already covers.
- **A second `subrosa-dev` scheme for debug builds.** It reads like it
  separates development from release and does not: same bundle identifier, one
  registration.
- **Auto-approving a pre-created request from the start link.** This is the
  attack above, written as a feature.
- **A one-time code sent by email.** A new authentication factor, with SMTP in
  a service that has none, new tables, and Keycloak's `auth_time`,
  `max_age=0` and `email_verified` invariants bypassed — to end up with an
  account that mailbox access alone can enter.
- **The password typed into the app (direct access grant).** Disabled on the
  Keycloak client, deprecated by OAuth 2.1, incompatible with passkeys and
  second factors, and it would put the password in the app's hands.
