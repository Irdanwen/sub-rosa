# Office add-ins (Word, Excel, PowerPoint)

Sub Rosa in a task pane beside a document (parity WP22,
[ADR-0102](adr/0102-an-office-task-pane-is-a-browser-device-whose-session-a-sign-in-window-carries.md)
and its addendum of 2026-10-10). The panes are served by an origin of their
own, `https://office.subrosa.furetier.com`, never by the account origin:
Microsoft's Office.js, which nobody can pin, runs in them.

| Host | What it does | Office API |
| --- | --- | --- |
| Word | Rewrite, shorten, correct, summarize or translate the selection, or apply a described change; draft text at the cursor (with the web search) | WordApi 1.1 |
| Excel | Explain the selected cell's formula; write a formula for the selected cell from a description; analyse the selected range with Python (Pyodide, when the browser allows it) and write the results to a new sheet | ExcelApi 1.4 |
| PowerPoint | Draft slides from a request, optionally from a pasted note, and add them after the selected slide in the presentation's theme | PowerPointApi 1.2 (1.5 to place them) |

Every answer is a proposal: the document changes only when you press
Replace, Insert, Put it in, Write to a new sheet or Add slides.

## How it signs in

Each pane is a browser device of your account, like a browser using
`/app` (ADR-0096): it has its own Carpe Diem key, limited per day, kept
encrypted in the pane's origin. The first time, press **Sign in**: a window
opens, you sign in on the Sub Rosa account site, then approve the add-in from
the Sub Rosa app (Settings, Account, Connect another device) with the code the
pane shows. The window closes by itself once the pane has its key. The key is
renewed while you use the add-in; the pane asks you to open the sign-in window
again when it is about to run out. A pane reads none of your notes, memories
or chats.

Under the hood the window runs on the office origin (it needs Office.js to
talk to the pane) and frames the account origin's `/office/courier.html`, a
page without Office.js that holds the session and carries the pane's seven
device calls; signing in is a visit to the account origin that comes back
through `/office/signed-in.html`. The pane never calls the account service
itself, so the recovery key cannot admit a pane on any platform (the code
would cross Office's channel): approve it from the app.

## Files

- `office-addins/manifests/word.xml`, `excel.xml`, `powerpoint.xml` (version
  1.0.1.0): one manifest per host, generated by
  `node office-addins/scripts/manifests.mjs` (`--check` fails when they are
  stale; `--origin https://… --account-origin https://… --out <dir>` writes
  copies for another pair of origins, such as staging). The panes are on the
  office origin; the account origin is in `<AppDomains>`.
- The office origin serves `/office/word.html`, `/office/excel.html`,
  `/office/powerpoint.html`, `/office/session.html` (the sign-in window),
  `/office/commands.html` (the ribbon button's function file), their assets
  and `/pyodide/` (the Excel pane's Python). `pnpm --filter
  @subrosa/office-addins build` writes them to `office-addins/dist`, with
  `office-addins/public/_headers` for a static host.
- The account origin serves `/office/courier.html` and
  `/office/signed-in.html` (built by the website, neither with Office.js) and
  `/office/moved.html`, where the add-ins' old addresses redirect.
- Both builds bake in the origins: the office build reads
  `VITE_ACCOUNT_ORIGIN` and `VITE_OFFICE_ORIGIN`, the website build
  `VITE_OFFICE_ORIGIN` only (the account website is built without
  `VITE_ACCOUNT_ORIGIN`). Unset, they are production's
  (`scripts/office-origins.mjs`).

## Sideloading

Download the manifest for the host you want from the repository (or build one
for your origin with `--origin`).

### Office on the web

1. Open a document in Word, Excel or PowerPoint on the web.
2. Home, **Add-ins**, **More add-ins** (or Insert, Add-ins), then **My
   add-ins**, **Upload my add-in**.
3. Choose the manifest file and press **Upload**. The Sub Rosa button appears
   on the Home tab.
4. Allow pop-ups for the Office site: the sign-in window is a pop-up.

### Windows (Microsoft 365, WebView2)

1. Create a folder, for example `C:\SubRosaAddins`, put the manifests in it,
   and share it (Properties, Sharing, Share) so it has a network path like
   `\\YOUR-PC\SubRosaAddins`.
2. In Word, Excel or PowerPoint: File, Options, Trust Center, Trust Center
   Settings, **Trusted Add-in Catalogs**. Add the network path, tick **Show in
   Menu**, press OK and restart the app.
3. Home, Add-ins (or Insert, My Add-ins), **Shared Folder**, choose Sub Rosa.

Office 2016 builds that still use Internet Explorer or the first Edge web view
cannot run the panes; Microsoft 365 with WebView2 can.

### Mac

1. Quit the app, then copy the manifest into its `wef` folder (create it if
   needed):
   - Word: `~/Library/Containers/com.microsoft.Word/Data/Documents/wef`
   - Excel: `~/Library/Containers/com.microsoft.Excel/Data/Documents/wef`
   - PowerPoint: `~/Library/Containers/com.microsoft.Powerpoint/Data/Documents/wef`
2. Open the app and a document, then Home, Add-ins (or Insert, My Add-ins) and
   choose Sub Rosa under the developer add-ins.

### iPad

Sideloading on iPad needs a manifest published through the Microsoft 365
admin center; the panes have not been checked there.

## Deployment

ADR-0096's gates still apply: Carpe Diem must hold the browser bound before
any pane can obtain a key ([browser-device-deployment.md](browser-device-deployment.md)).
Then, in this order (the account side of each step is in
[vps-account-stack.md](vps-account-stack.md), section "Origine des
compléments Office"):

0. **Carpe Diem (external gate).** Add `https://office.subrosa.furetier.com`
   to `SUBROSA_SITE_ORIGINS` in the operator's `browserKeys.ts` and deploy it:
   Carpe Diem admits browser calls by origin, and without it every call of a
   pane is refused by CORS. Check:
   ```sh
   curl -si -X OPTIONS https://carpe-diem.xyz/api/operator/partner/keys \
     -H 'Origin: https://office.subrosa.furetier.com' \
     -H 'Access-Control-Request-Method: POST' \
     -H 'Access-Control-Request-Headers: authorization,dpop,content-type' \
     | grep -i '^access-control-allow-origin: https://office.subrosa.furetier.com'
   ```
1. **DNS.** An `A` record (and `AAAA` if the VPS has one) for
   `office.subrosa.furetier.com` to the VPS, not proxied, so the ACME
   challenge reaches nginx. Check: `dig +short office.subrosa.furetier.com`.
2. **Port-80 vhost for the ACME challenge.**
   ```sh
   sed 's/office.example.invalid/office.subrosa.furetier.com/g' \
     subrosa-cloud/deploy/nginx-office-bootstrap.conf.example \
     > /etc/nginx/sites-available/subrosa-office
   ln -s /etc/nginx/sites-available/subrosa-office /etc/nginx/sites-enabled/
   mkdir -p /var/www/certbot && nginx -t && systemctl reload nginx
   ```
3. **Certificate, by webroot.**
   `certbot certonly --webroot -w /var/www/certbot -d office.subrosa.furetier.com`.
   Renewals reload nginx through `subrosa-cloud/deploy/renew-certificate.sh`;
   if it is not already in `/etc/letsencrypt/renewal-hooks/deploy/` for the
   other origins, pass it with `--deploy-hook`.
4. **Build both, each with its origins**, on the build machine:
   ```sh
   VITE_OFFICE_ORIGIN=https://office.subrosa.furetier.com \
     pnpm --filter @subrosa/website build
   VITE_ACCOUNT_ORIGIN=https://subrosa.furetier.com \
   VITE_OFFICE_ORIGIN=https://office.subrosa.furetier.com \
     pnpm --filter @subrosa/office-addins build
   grep -l 'https://office.subrosa.furetier.com' website/dist/assets/office-origins-*.js
   grep -l '"https://subrosa.furetier.com"' office-addins/dist/office/assets/*.js
   ```
   Never set `VITE_ACCOUNT_ORIGIN` on the website build: it would make the
   account site send its own pages to another origin.
5. **Publish the office build** to `/srv/subrosa-office/www/current`, as a
   release directory switched by a link:
   ```sh
   id=$(date -u +%Y%m%dT%H%M%SZ)
   ssh root@VPS mkdir -p /srv/subrosa-office/www/releases
   rsync -a --delete office-addins/dist/ root@VPS:/srv/subrosa-office/www/releases/$id/
   ssh root@VPS "cd /srv/subrosa-office/www && ln -sfn releases/$id current.new && mv -Tf current.new current"
   ```
6. **HTTPS vhost**, replacing the bootstrap file:
   ```sh
   sed -e 's/office.example.invalid/office.subrosa.furetier.com/g' \
       -e 's/account.example.invalid/subrosa.furetier.com/g' \
     subrosa-cloud/deploy/nginx-office.conf.example \
     > /etc/nginx/sites-available/subrosa-office
   nginx -t && systemctl reload nginx
   ```
   Check: `curl -sI https://office.subrosa.furetier.com/office/word.html`
   sends the policy with `frame-src 'self' https://appsforoffice.microsoft.com
   https://subrosa.furetier.com/office/courier.html`, no `X-Frame-Options` and
   no `Set-Cookie`; `/api/v1/me` there answers 404.
7. **Service release** with `/office/signed-in.html` in `RETURN_TO`
   (`subrosa-cloud/crates/services/src/lib.rs`). Check:
   `curl -s -o /dev/null -w '%{http_code}\n' 'https://subrosa.furetier.com/auth/login?return_to=/office/signed-in.html'`
   redirects (302 or 303); with `return_to=/office/session.html` it answers
   400.
8. **Account site release**, right after the service: publish
   `website/dist` as usual, and install the account vhost from
   `nginx-account.conf.example` (its courier, signed-in and moved locations
   replace the old `/office/` block; substitute both hosts), then
   `nginx -t && systemctl reload nginx`. Check:
   `curl -sI https://subrosa.furetier.com/office/courier.html` sends
   `frame-ancestors https://office.subrosa.furetier.com`, `Cache-Control:
   no-store` and no `X-Frame-Options`; `curl -sI
   https://subrosa.furetier.com/office/word.html` answers 308 to
   `/office/moved.html`; no response of the account origin names
   `appsforoffice`.
9. **Manifests.** `node office-addins/scripts/manifests.mjs --check`, then
   `npx office-addin-manifest validate office-addins/manifests/<host>.xml`
   for each host (it calls Microsoft's online service).
10. **Re-sideload** each manifest on Windows, Mac and the web (below),
    after removing the old add-in, then sign in and approve each pane once.
    Revoke the old "Office add-in" devices from the app or
    `/account/devices`.

What a person sees at the cutover: an add-in sideloaded before 1.0.1.0 shows
"Sub Rosa for Office has moved" with a link to the new manifests; the new
add-in asks to sign in and to be approved from the app once more, on every
platform, desktop included (desktop panes no longer sign in in place, and no
longer offer the recovery key); the old pane devices stay in the device list
until revoked, and their keys stop within seven days. Nothing changes for the
site or `/app`.

## What was checked, and what was not

Nothing has run inside real Office yet. Checked when written (2026-10-08):

- unit tests with Office.js replaced (`src/test/office-addins-*.test.ts*`):
  selection reads, proposals applied only after confirmation, a moved
  selection refused, the analysis range mounted for Python, formulas and
  sheets written where the proposal said, slides inserted after the selected
  one, the sign-in window's relay and its refusals, the manifests' schema
  order, resources and URLs;
- `npx office-addin-manifest validate` on the three manifests: valid (it
  calls Microsoft's online validation service, so it is not an offline check);
- `node office-addins/scripts/smoke.mjs` with Playwright's headless Chromium
  over both origins on two local ports (`subrosa.furetier.test` and
  `office.subrosa.furetier.test`, same site like production), each with the
  headers of its `_headers` file and a stand-in for the service: each pane
  renders with a stubbed Office.js and calls no account API; the sign-in
  window frames the courier, signs in on the account origin, comes back
  through `signed-in.html`, and a pane's call is carried with the account's
  cookie, CSRF token and origin while a call outside the seven is refused;
  the office origin never receives the account cookie; another site cannot
  frame the courier; the old addresses lead to the moved page. With
  Microsoft's real Office.js (`--real-office-js`) the panes render outside
  Office with no violation but the telemetry frame the policy refuses on
  purpose (re-run on 2026-10-10 on the office origin).

To check by hand on each of Windows, Mac and the web before announcing:
the pane loads (frame-ancestors on the web), the sign-in window opens, frames
the courier (Office's desktop dialogs included) and closes itself, a pairing
approved from the app gives the pane a key, each action proposes then
applies, Python runs in the Excel pane, and Office still works with its
telemetry frame refused.

## External gate: AppSource

Publishing in Microsoft's store (AppSource) is outside this repository: a
Partner Center publisher account, the store's validation of each manifest
(including its policies on privacy statement, support URL, and test
credentials for the reviewers), and Microsoft's review. Until then the add-ins
are installed by sideloading, or by an organisation's administrator through
the Microsoft 365 admin center.

## Languages

The panes use the site's copy (`t()` of `website/src/lib/i18n.ts`) in English
and French, following Office's display language. German, Italian, Spanish and
Brazilian Portuguese follow when the site's catalog gains them. The manifests
carry English and French names and descriptions.
