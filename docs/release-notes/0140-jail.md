# Notes de version proposées : le bac à sable de l'assistant (ADR-0140)

Correctif de sécurité de la 1.97.0. Il concerne l'assistant sur Mac, en
session « bac à sable » (le mode par défaut).

## Français

### Ce qui est corrigé

- Une session en bac à sable pouvait écrire des fichiers que d'autres parties
  de Sub Rosa lisent et exécutent ensuite hors du bac à sable : réglages,
  routines, extensions, scripts, connexions. Elle a désormais son propre
  dossier, séparé de celui du côté sans restriction, des routines et des
  messageries, et ne peut plus rien y écrire de ce qui s'exécute ailleurs.
- Elle ne peut plus lancer ni piloter d'autres programmes : ouvrir une
  application ou un lien, AppleScript, Raccourcis, éléments d'ouverture,
  menu Services, frappes ou clics simulés, captures d'écran, presse-papiers.
  Elle n'hérite plus des autorisations de Sub Rosa (Accessibilité,
  enregistrement de l'écran).
- Elle ne peut plus joindre l'agent ssh ou gpg, Docker et les autres moteurs
  de conteneurs, un multiplexeur de terminal, ni un service local de cette
  machine autre que ceux dont elle a besoin, ni envoyer de datagramme
  (UDP). Elle n'écrit plus dans les dossiers temporaires partagés.
- Un dossier que macOS ou vos programmes lisent à l'ouverture de session
  (`~/Library/LaunchAgents`, `Application Support`, `Preferences` et
  voisins) ne peut plus être choisi comme dossier de travail.
- Sub Rosa n'exécute plus `git` sur le dossier de travail d'une session sans
  protection : un réglage planté dans `.git/config` par une session
  (présent depuis la 1.97.0) ne s'exécute plus quand la revue de code ou le
  conseil lisent ce dossier. Un dossier dont la configuration git définit un
  programme (un filtre, une commande de comparaison) n'est plus lu du tout,
  et git y tourne dans un bac à sable qui ne lit que le dépôt et ne joint
  aucun réseau.
- À l'arrêt de l'assistant, les processus qu'une session en bac à sable a
  laissés derrière elle sont arrêtés, même détachés.
- Chaque conversation est lue dans le dossier de son mode, jamais dans
  l'autre.

### Ce qu'il faut refaire

Au premier lancement, un avis dit ce qui a été mis de côté et ce qu'il faut
refaire. Selon votre installation :

- associer de nouveau vos messageries ;
- réinstaller les serveurs MCP du catalogue ;
- vous reconnecter aux connecteurs qui demandaient une connexion, depuis une
  session en bac à sable (les connexions ne sont plus partagées entre les
  deux côtés) ;
- vos tableaux de tâches, routines à script, extensions et scripts ont été
  mis de côté, jamais supprimés : vous pouvez les remettre un par un, après
  confirmation, depuis l'avis ;
- l'ancien dossier de l'assistant est l'« Unrestricted workspace » du
  panneau Fichiers.

En session en bac à sable, ces actions ne marchent plus : ouvrir un lien ou
une application depuis un outil (l'assistant vous donne le lien), le
presse-papiers, les notifications, les captures, écrire dans `/tmp` par son
nom, joindre une base de données locale ou un serveur local lancé par la
session, l'agent ssh. Pour en avoir besoin, démarrez une session sans
restriction.

La revue de code et le conseil ne lisent plus un dépôt qui définit un
programme dans sa propre configuration git (un filtre comme celui de
git-lfs installé dans le dépôt, une commande de comparaison) : ils le
disent au lieu de le lire.

### Ce qui reste ouvert

- Windows n'a pas de bac à sable.
- Le dossier de travail reste écrit par la session : ce que vos propres
  outils y exécutent ensuite (votre `git`, `direnv`, un script de build) est
  hors de ce correctif.
- Les adresses d'un VPN ou de Tailscale sur ce Mac n'ont pas été mesurées
  contre la règle de la boucle locale : la règle réseau du bac à sable ne
  sait nommer que « cette machine » ou « tout », jamais une adresse.
- Un programme qui parlerait lui-même le protocole privé de launchd pourrait
  arrêter, relancer ou désactiver un de vos agents ou Sub Rosa (une gêne,
  pas un programme lancé hors du bac à sable).
- Un processus qui se détache à chaque fork plus vite qu'un balayage peut
  survivre à l'arrêt, toujours dans le bac à sable, sans aucune autorisation
  de Sub Rosa.

## English

### Fixed

- A sandboxed session could write files that other parts of Sub Rosa read
  and then run outside the sandbox: settings, routines, plugins, scripts,
  sign-ins. It now has a folder of its own, apart from the unrestricted
  side, routines and messaging, and can write nothing there that runs
  elsewhere.
- It can no longer start or drive other programs: opening an app or a link,
  AppleScript, Shortcuts, login items, the Services menu, simulated keys or
  clicks, screenshots, the clipboard. It no longer inherits Sub Rosa's
  permissions (Accessibility, screen recording).
- It can no longer reach the ssh or gpg agent, Docker and other container
  engines, a terminal multiplexer, or a service of this Mac other than the
  ones it needs, or send a datagram (UDP). It no longer writes the shared
  temporary folders.
- A folder macOS or your programs read at login (`~/Library/LaunchAgents`,
  `Application Support`, `Preferences` and the like) can no longer be
  picked as a working folder.
- Sub Rosa no longer runs `git` on a session's working folder unprotected: a
  setting a session planted in `.git/config` (present since 1.97.0) no
  longer runs when the code review or the council reads that folder. A
  folder whose git configuration defines a program (a filter, a diff
  command) is not read at all, and git runs there in a sandbox that reads
  only the repository and reaches no network.
- When the assistant stops, the processes a sandboxed session left behind
  are stopped, detached ones included.
- Each conversation is read from the folder of its own mode, never the
  other one.

### What to redo

At first launch a notice says what was set aside and what to redo.
Depending on your setup:

- pair your messaging channels again;
- install the catalog MCP servers again;
- sign in again, from a sandboxed session, to the connectors that asked you
  to (sign-ins are no longer shared between the two sides);
- your task boards, script routines, plugins and scripts were set aside,
  never deleted: you can put them back one by one, after a confirmation,
  from the notice;
- the assistant's former folder is the "Unrestricted workspace" of the
  Files panel.

In a sandboxed session these no longer work: opening a link or an app from
a tool (the assistant gives you the link), the clipboard, notifications,
screenshots, writing `/tmp` by name, reaching a local database or a local
server the session started, the ssh agent. When you need them, start an
unrestricted session.

The code review and the council no longer read a repository that defines a
program in its own git configuration (a filter such as git-lfs installed in
the repository, a diff command): they say so instead of reading it.

### Still open

- Windows has no sandbox.
- The working folder is still written by the session: what your own tools
  later run from it (your `git`, `direnv`, a build script) is outside this
  fix.
- A VPN's or Tailscale's addresses on this Mac were not measured against the
  loopback rule: the sandbox's network rule can name only "this machine" or
  "everything", never an address.
- A program that speaks launchd's private protocol itself could stop,
  restart or disable one of your agents or Sub Rosa (a nuisance, not a
  program run outside the sandbox).
- A process that detaches again at every fork, faster than a sweep, can
  outlive the stop, still in the sandbox, with none of Sub Rosa's
  permissions.
